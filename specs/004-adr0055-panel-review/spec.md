# Feature Specification: Discover, Fix, Verify Panel Review

**Feature Branch**: `spec004-panel-review-pragmatic`

**Created**: 2026-08-08

**Status**: Draft

**Input**: Implement accepted ADR 0055 as a pragmatic standard Copilot panel workflow.

## User Scenarios & Testing

### User Story 1 - Batch Panel Findings (Priority: P1)

A contributor runs one comprehensive panel discovery and receives one
deduplicated issue ledger with stable identifiers, severities, impact, and
recommended fixes.

**Why this priority**: A complete shared ledger is the core improvement that
replaces repeated rediscovery and enables efficient batch fixes.

**Independent Test**: Run discovery against a candidate with overlapping
reviewer findings and confirm that every source finding maps to one stable
ledger item without losing attribution.

**Acceptance Scenarios**:

1. **Given** a candidate ready for review, **When** the panel runs discovery,
   **Then** every selected reviewer receives the full candidate and is asked
   for a comprehensive review.
2. **Given** duplicate findings from multiple reviewers, **When** discovery
   results are merged, **Then** they map to one stable issue while retaining
   every source attribution.
3. **Given** identical discovery inputs, **When** artifacts are regenerated,
   **Then** identifiers and generated bytes are unchanged.
4. **Given** a selected reviewer finds no issues, **When** discovery is
   collected, **Then** its explicit complete result with zero findings is
   accepted and is distinguishable from a missing reviewer result.

---

### User Story 2 - Fix and Verify the Ledger (Priority: P1)

An implementation agent receives the complete ledger, records a disposition
for every issue, performs self-verification, and sends reviewers generated
verification artifacts containing the prior issues and responses.

**Why this priority**: Review convergence improves only when fixes are batched
and later reviews verify known issues instead of reopening discovery.

**Independent Test**: Resolve a sample ledger in one implementation pass and
confirm that verification receives every stable issue, disposition, evidence,
and previous status.

**Acceptance Scenarios**:

1. **Given** a complete ledger, **When** implementation prepares verification,
   **Then** no issue can silently disappear and every issue has a supported
   disposition.
2. **Given** completed fixes, **When** verification runs, **Then** reviewers
   verify prior findings, dispositions, evidence, and introduced regressions.
3. **Given** a pre-existing MINOR or NIT missed during discovery, **When**
   verification notices it, **Then** it does not become a new blocking issue.
4. **Given** unresolved merge-blocking conditions, **When** verification
   completes, **Then** sign-off remains false.
5. **Given** a BLOCKER response, **When** approval is evaluated, **Then** only
   Fixed, or Invalid or Withdrawn with verified factual status, can approve it.
6. **Given** a MAJOR response, **When** approval is evaluated, **Then** it is
   Fixed or carries recorded acceptance by the repository maintainer or merge
   owner; Deferred alone cannot approve it.

---

### User Story 3 - Select Relevant Experts and Continue Legacy Work (Priority: P2)

A contributor gets a deterministic reviewer roster appropriate to the changed
surface, including build expertise when triggered, while panel loops already
in progress continue automatically under the new lifecycle.

**Why this priority**: The workflow must improve expertise without forcing
contributors to restart existing reviews or manually reconstruct context.

**Independent Test**: Exercise representative candidate classifications and
legacy records, then confirm deterministic roster selection and stable
conversion into current artifacts.

**Acceptance Scenarios**:

1. **Given** a build-system or build-contract change, **When** the roster is
   selected, **Then** the build expert is included.
2. **Given** ambiguous candidate classification, **When** the roster is
   selected, **Then** the wider applicable roster is used.
3. **Given** a completed legacy round, **When** it is imported, **Then** it
   becomes the discovery input without rerunning discovery.
4. **Given** a partial legacy round, **When** it is imported, **Then** completed
   findings are retained before one current discovery panel runs.
5. **Given** a lifecycle selection artifact, **When** panel request and record
   generation consume it, **Then** both require its candidate, selection-schema
   version, selection-table version, and ordered roster to match their own
   inputs.

### Edge Cases

- Conflicting existing generated bytes cause a clear failure instead of being
  overwritten.
- A fix activates another expert; that expert joins verification and no prior
  reviewer leaves the lifecycle.
- A fix contains unrelated scope expansion; verification preparation refuses
  it and directs the contributor to a new or explicitly rescoped lifecycle.
- Legacy severity text lacks a recognized bracketed prefix; it is imported as
  migration-assigned MAJOR while preserving the raw source text.
- A selected seat has no discovery result; generation refuses the lifecycle
  rather than treating absence as zero findings.
- A ledger issue has no implementation response, or a response omits required
  justification, evidence, factual verification, or acceptance; verification
  preparation refuses the incomplete artifact.
- A selected seat returns an explicit complete discovery result with an empty
  findings list; it is accepted as a positive zero-finding result.
- No implementation iteration has occurred; the average fixed-per-iteration
  metric is `0.0`.

## Requirements

### Functional Requirements

- **FR-001**: The workflow MUST run exactly one comprehensive discovery panel
  per lifecycle.
- **FR-002**: Every selected discovery reviewer MUST receive the full candidate,
  relevant context, validation evidence, and seat-specific guidance.
- **FR-003**: Discovery reviewers MUST report all reasonably discoverable
  actionable findings with severity, impact, and a concrete recommendation.
- **FR-004**: The orchestrator MUST merge all discovery findings into one
  deduplicated ledger with deterministic stable identifiers.
- **FR-005**: Every source finding MUST map to exactly one ledger issue while
  preserving its reviewer attribution.
- **FR-006**: Every ledger issue MUST record one supported disposition before
  verification: Fixed, Intentionally rejected, Deferred, Withdrawn, or Invalid.
- **FR-007**: The workflow MUST capture applicable validation and implementation
  self-review evidence before panel verification.
- **FR-008**: Verification reviewers MUST receive the complete ledger,
  implementation responses, evidence, latest delta, full candidate context,
  and their prior obligations.
- **FR-009**: Verification MUST focus on issue resolution, dispositions,
  evidence, regressions, and unsafe late BLOCKER or MAJOR findings.
- **FR-010**: Verification MUST reject new pre-existing MINOR or NIT findings
  and other optional improvements as blocking recommendations.
- **FR-011**: Sign-off MUST remain equivalent to an empty blocking
  recommendation list.
- **FR-012**: The workflow MUST automatically generate lifecycle selection,
  discovery, ledger, implementation-response, and per-reviewer verification
  artifacts.
- **FR-013**: Artifact generation MUST be deterministic and MUST refuse
  conflicting regeneration.
- **FR-014**: Reviewer selection MUST use one versioned deterministic source
  for seat classes, minimum roster sizes, fill order, profiles, focus, and
  triggers.
- **FR-015**: Every panel MUST include mandatory experts, every triggered
  optional expert, and at least the minimum roster for its candidate class.
- **FR-016**: Build-system, build-orchestration, build-contract, dependency,
  packaging, and release-artifact changes MUST select build expertise.
- **FR-017**: Candidate ambiguity MUST widen rather than narrow reviewer
  selection.
- **FR-018**: After discovery, reviewer selection MUST rerun for the full
  candidate and each fix delta, and the lifecycle roster MUST only widen.
- **FR-019**: The workflow MUST automatically import completed and partial
  legacy rounds without dropping completed findings or fixes underway.
- **FR-020**: Repeated legacy imports MUST produce stable source identities,
  mappings, and generated bytes.
- **FR-021**: Legacy raw recommendation text and attribution MUST remain
  unchanged in imported evidence.
- **FR-022**: The workflow MUST record initial findings, late findings, late
  BLOCKER and MAJOR counts, review iterations, implementation iterations, and
  average fixed issues per implementation iteration.
- **FR-023**: Metrics MUST be informational and MUST NOT become approval
  thresholds or reviewer scores.
- **FR-024**: The implementation MUST use the existing contributor tooling and
  MUST NOT add a daemon, privileged service, broker surface, operating-system
  principal, or runtime product surface.
- **FR-025**: Gas City implementation MUST remain out of scope while future
  producers can consume the same selection and artifact contracts.
- **FR-026**: Every selected discovery seat MUST supply an explicit complete
  result; a complete result with zero findings MUST be accepted, while an
  absent result MUST be refused.
- **FR-027**: Every ledger issue MUST have exactly one implementation response
  with the justification and evidence required by its disposition; omission
  MUST fail closed.
- **FR-028**: Approval MUST require every BLOCKER to be Fixed, or Invalid or
  Withdrawn based on verified factual status. Intentionally rejected and
  Deferred MUST NOT approve a BLOCKER.
- **FR-029**: Approval MUST require every MAJOR to be Fixed or to carry
  recorded acceptance by the repository maintainer or merge owner. Deferred
  MUST NOT approve an unaccepted MAJOR.
- **FR-030**: Each reviewed candidate state MUST have exactly one versioned
  selection artifact bound to its lifecycle identifier, candidate digest
  triple, selection-table version, profiles, and ordered lifecycle roster.
- **FR-031**: Both xtask `delivery wave panel-request` and
  `make-records.mjs` MUST consume that same selection artifact and MUST refuse
  candidate, selection-schema version, selection-table version, or ordered
  roster disagreement.
- **FR-032**: xtask `delivery wave panel-request --selection` MUST populate the
  existing schema-version-2 request's `roles` and `record_files` from the
  validated selection, and `make-records.mjs` MUST emit the existing
  schema-version-2 `PanelRecord` shape for exactly those roles.
- **FR-033**: `panel-attest` MUST validate exactly the ordered roster already
  stored in the panel request. Existing schema-version-2 request, record,
  attestation, and seal shapes MUST NOT gain lifecycle, selection digest, or
  panel-version fields. Existing ten-seat requests and records, including
  `rust`, MUST remain readable through the same types; the allowed role domain
  retains Rust while current selection excludes it.
- **FR-034**: The build seat prompt and source guidance MUST be added to
  `docs/adr/specs/0053-panel-prompt-sources.md`, and prompt-corpus shape checks
  and tests MUST account for the resulting 35-file corpus with sixteen agent
  files.

### Key Entities

- **Panel Lifecycle**: One discovery, its stable roster, fix iterations,
  verification iterations, artifacts, and metrics.
- **Source Finding**: One reviewer observation with immutable source identity,
  raw text, attribution, severity, impact, and recommendation.
- **Issue Ledger**: Deduplicated issues with stable identifiers and complete
  source mappings.
- **Implementation Response**: One disposition, justification, changed surface,
  evidence, optional verified factual status, and optional recorded maintainer
  or merge-owner acceptance for a ledger issue.
- **Reviewer Selection**: Versioned seat definitions, triggers, profiles, floors,
  and deterministic selected roster.
- **Lifecycle Selection Artifact**: The single artifact shape for a
  candidate-bound and lifecycle-bound current selection, including its schema
  version, selection-table version, profiles, and ordered roster.
- **Review Artifact**: Generated discovery or verification input bound to one
  lifecycle and candidate state.

## Success Criteria

### Measurable Outcomes

- **SC-001**: One discovery run accounts for 100 percent of selected reviewer
  outputs in the shared ledger.
- **SC-002**: Identical inputs produce identical issue identifiers, source
  mappings, and generated artifacts in 100 percent of repeated runs.
- **SC-003**: Every verification request contains all prior ledger issues and
  all recorded implementation responses without operator hand-copying.
- **SC-004**: Representative roster tests cover every mandatory seat, every
  optional trigger, both roster floors, ambiguity widening, and build expertise.
- **SC-005**: Complete and partial legacy fixtures convert without losing any
  completed source finding and remain stable across repeated imports.
- **SC-006**: Verification cannot block approval with a newly reported
  pre-existing MINOR or NIT issue.
- **SC-007**: A merge-ready candidate receives unanimous lifecycle-roster
  sign-off without requiring another discovery pass.
- **SC-008**: The delivered change adds zero privileged services, runtime
  daemons, operating-system principals, or product control-plane surfaces.
- **SC-009**: Candidate, selection-schema, selection-table-version, ordered
  roster, missing or extra record, and mismatched-selection cases fail in the
  responsible panel-request, record-generation, or panel-attest tests.
- **SC-010**: Existing test helpers prove schema-version-2 delivery shapes are
  unchanged and a ten-seat request and record set including `rust` remains
  readable without a new fixture family.
- **SC-011**: Planted negatives refuse a missing selected-seat discovery
  result, a missing ledger response, and incomplete required justification or
  evidence, while a complete zero-finding seat result passes.
- **SC-012**: Approval tests accept verified BLOCKER and accepted MAJOR cases
  and refuse Deferred BLOCKER and unaccepted Deferred MAJOR cases.

## Assumptions

- ADR 0055 is accepted and defines the binding workflow and reviewer-selection
  contract.
- Existing staged-diff, reviewer-agent, model-binding, and verdict-record
  mechanisms remain the implementation base.
- The orchestrating agent assigns stable issue identifiers and may use LLM
  judgement to deduplicate findings.
- Ordinary repository history and review controls provide sufficient
  auditability for this quality gate.
- The first implementation targets the standard Copilot panel skill only.
